## Declaração constitucional

Este documento estabelece o modelo executivo para a implementação controlada da estrutura física permanente do Portal da FESTANÇA.

Sua função é transformar a arquitetura documental consolidada em uma estrutura real de diretórios, arquivos-base, componentes compartilhados, edições anuais e caminhos institucionais permanentes.

Nenhuma estrutura será criada com base apenas em suposição documental.

Nenhum diretório será criado antes da confirmação de que não existe estrutura equivalente.

Nenhum arquivo será substituído silenciosamente.

Nenhum componente fundador será removido.

Nenhuma referência será alterada sem rastreabilidade.

Nenhuma edição anual será incorporada ao Portal Permanente de modo irreversível.

A FESTANÇA 2026 deverá permanecer integralmente:

- preservada;
- identificável;
- recuperável;
- reconstruível;
- versionada;
- auditável;
- historicamente contextualizada;
- separada da camada permanente;
- vinculada à arquitetura futura;
- protegida contra sobrescrita.

A execução física somente poderá ocorrer após:

- conclusão real do F5-P2;
- emissão de parecer favorável de prontidão;
- conclusão real do F5-P3;
- confirmação da linha de base;
- aprovação dos blocos;
- validação das dependências;
- autorização humana expressa.

A mera publicação deste documento não autoriza a criação física de diretórios ou arquivos.

# 7. Princípio da estrutura real

Nenhuma estrutura documental será automaticamente considerada estrutura física existente.

Todo diretório deverá ser classificado como:

- existente;
- inexistente;
- equivalente;
- divergente;
- duplicado;
- órfão;
- candidato à criação;
- bloqueado;
- fundador.

---

# 8. Princípio da menor intervenção

A implementação deverá utilizar a menor quantidade possível de alterações.

Antes de criar um novo caminho, deverá ser verificado:

- se já existe;
- se existe caminho equivalente;
- se existe arquivo com nome semelhante;
- se há dependências;
- se o caminho está documentado;
- se a criação causará duplicidade;
- se a edição fundadora já utiliza outro caminho.

---

# 9. Princípio da separação arquitetural

A arquitetura deverá distinguir:

```text
PORTAL PERMANENTE
+
EDIÇÕES ANUAIS
+
COMPONENTES COMPARTILHADOS
+
ACERVO HISTÓRICO
+
DADOS E METADADOS
+
DOCUMENTAÇÃO
```

Nenhuma edição anual deverá ser tratada como a totalidade do Portal Permanente.

---

# 10. Princípio da não sobrescrita

É proibido:

- criar arquivo sobre arquivo existente;
- redirecionar conteúdo para caminho ocupado;
- substituir arquivo sem inventário;
- mover arquivo sem registrar origem;
- renomear sem validar dependências;
- eliminar componente anterior;
- reutilizar nome com significado diferente;
- apagar referência fundadora.

---

# 11. Princípio da compatibilidade

Toda criação deverá ser compatível com:

- estrutura atual;
- GitHub;
- Termux;
- navegadores modernos;
- Firebase, quando aplicável;
- arquivos estáticos;
- dados JSON;
- caminhos relativos;
- histórico do Git;
- documentação institucional;
- edição fundadora.

---

# 12. Princípio da reversibilidade

Toda criação deverá poder ser revertida sem:

- perda de arquivo;
- perda de referência;
- perda de histórico;
- perda de evidência;
- quebra da FESTANÇA 2026;
- comprometimento do repositório;
- alteração irreversível de dados.

# 13. Regimes operacionais

## 13.1. Regime R0 — Planejamento

Permite:

- mapear;
- comparar;
- classificar;
- documentar;
- preparar blocos.

Não permite alteração física.

## 13.2. Regime R1 — Somente leitura

Permite:

- listar;
- localizar;
- contar;
- inspecionar;
- validar;
- produzir evidências.

## 13.3. Regime R2 — Criação controlada

Permite, mediante autorização:

- criar diretórios inexistentes;
- criar arquivos novos;
- criar arquivos-base;
- criar marcadores estruturais.

## 13.4. Regime R3 — Integração controlada

Permite, em ciclo posterior:

- integrar arquivos existentes;
- atualizar referências;
- conectar componentes.

## 13.5. Regime R4 — Publicação

Não integra o escopo inicial deste ciclo.

Somente após autorização:

```bash
mkdir CAMINHO_APROVADO
```

- não utilizar `mkdir -p` inicialmente;
- criar um nível por bloco;
- validar imediatamente;
- não criar múltiplos diretórios em um único comando;
- registrar o resultado.
